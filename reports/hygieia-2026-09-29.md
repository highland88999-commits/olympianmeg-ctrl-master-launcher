## What it is

HYGIEIA (Greek goddess of health) — a health pocket universe at `/hygieia` with two sections:

1. **Programmable reminders (per-user):** create / edit / delete / enable-disable, with `once`, `daily`, and `weekly` (choose days) schedules plus a time. Backed by the new `reminder_items` Supabase table (`supabase/hygieia.sql`). Notification delivery is **stub only** — `lib/hygieia/notify.ts` is a documented stub whose `scheduleLocalReminder()` always declines and returns the honest line the UI shows verbatim: *"Reminders show in-app for now — phone notifications come with the mobile app."* A "Due now" strip on the page shows reminders whose time has come while the page is open (pure local-time math, never presented as phone push).
2. **Health dashboard (per-user):** reads the `user_steps` table — **does not redefine it** (see dependency note below). Shows personal totals (today / last 7 days / all time), a manual "log today's steps" field (upsert), and full history. "Room to grow" section lists **Sleep** and **Water** as static placeholders clearly marked "Coming later" — no fake inputs.

**PARKED by Merlin 2026-09-29: step-to-credit currency. No currency of any kind until he calls it.** Recorded in `lib/hygieia/notes.ts` (as the exported `PARKED_IDEAS` value and a code comment) and here. The module contains zero currency language — enforced by a headless test that fails if any token/credit/wallet/coin wording appears outside the parked note.

## Dependency note (parallel workstream)

`supabase/steps.sql` (user_steps: `user_id`, `step_date`, `steps`, owner-only RLS, PK on `(user_id, step_date)`, plus a `global_step_totals` aggregate view) already exists in the worktree from the parallel workstream. HYGIEIA's dashboard **only reads** `user_steps` (and upserts today's row, which the table's PK design explicitly supports: "Today is entered by hand"). `supabase/hygieia.sql` does **not** recreate or alter `user_steps` — a headless test asserts no `CREATE TABLE … user_steps` appears in it. Both SQL files are idempotent (`CREATE TABLE IF NOT EXISTS` + `DROP POLICY IF EXISTS`) and safe to run in either order.
